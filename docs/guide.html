CSS-LAB-BOA / student guide

Learn buffer overflows by breaking them yourself.

Seven short levels. Each one is a real, intentionally broken C program running in an isolated sandbox — you feed it input, watch it fail, then see exactly why the fixed version doesn't.

the idea in one minute

A buffer is a fixed-size chunk of memory — say, 16 bytes for a name. C does not stop you from writing 40 bytes into it. The extra bytes spill into whatever memory sits next door: another variable, or — on the stack — the address the function is supposed to return to when it's done. Overwrite that address, and you can redirect what the program does next.

Every level below follows the same shape: a function that can be used safely but isn't, an input that proves it, and a safe rewrite sitting right next to it.

the levels

01

gets() — unbounded read

›

gets() reads a line from input with no idea how big the destination buffer is — there's no length argument to give it one. It was removed from the C standard entirely because it cannot be used safely.

gets(buffer); // buffer[16], no size check possible
TRY IT · pipe a 40-character string instead of a short name

The fix swaps in fgets(buffer, sizeof(buffer), stdin), which always knows its own limit.

02

strcpy() — unchecked copy

›

Copies a string until it hits a null byte — never checking whether the destination has room for what it's copying.

strcpy(dest, source); // copies all of source, regardless of dest's size
TRY IT · pass a source string longer than the destination buffer

Fix: strncpy(dest, source, sizeof(dest)-1), length-capped.

03

strcat() — unchecked concatenation

›

Appends one string to the end of another, starting at the existing string's null terminator — with no sense of how much room is left.

strcat(dest, suffix);
TRY IT · concatenate past the destination's remaining capacity

Fix: strncat(dest, suffix, remaining_space).

04

sprintf() — oversized formatted output

›

Formats values into a buffer with no limit on how long the result can get. A wide number, a long %s, or many arguments can all push past the buffer's end.

sprintf(buf, "%s", long_input);
TRY IT · supply a long string for the %s argument

Fix: snprintf(buf, sizeof(buf), ...) — caps the output at the buffer's real size.

05

memcpy() — incorrect byte count

›

Copies exactly the number of bytes you tell it to — correctly. The bug isn't the function, it's trusting a byte count that came from untrusted input.

memcpy(buf, data, user_supplied_len); // len never validated
WIN CONDITION · overflow into the adjacent variable to flip access_granted

Fix: clamp len to sizeof(buf) before copying — bounds checking the count, not the function.

06

array indexing — invalid index

›

C performs no bounds checking on arr[i] at all — a negative or oversized i reads or writes memory relative to the array, wherever that lands.

arr[user_index] = value; // no range check on user_index
TRY IT · a negative index, not just one that's too large — ASan catches both

Fix: validate 0 <= i < size before every access.

07

return-address overwrite bonus

›

The deepest level: overflow far enough past a buffer to overwrite the function's saved return address, redirecting execution into secret_win() — compiled into the binary but never called by the program itself.

This level runs with stack canaries, PIE, and ASLR deliberately disabled inside the sandbox, so the raw mechanism is visible. It's the one place in this lab those protections are switched off — everywhere else they're left on.

GOAL · redirect control flow without ever calling secret_win() directly

how to run a level

Every level has a vuln.c and a secure.c. From inside the sandbox:

cd /opt/levels/01-gets gcc -g -fsanitize=address -fno-stack-protector -o /tmp/vuln vuln.c echo "normal input" | /tmp/vuln # should behave fine python3 -c "print('A'*40)" | /tmp/vuln # should trip ASan

Then compare against the fix the same way, using secure.c instead.

faq

Is it actually safe to run broken code like this?

Yes, inside the sandbox. Each session runs in a disposable Docker container with no network access, a read-only filesystem outside a small scratch area, and hard CPU/memory/process limits. Nothing escapes, nothing persists. Never run these binaries outside the provided container.

What is AddressSanitizer (ASan)?

A compiler instrumentation (-fsanitize=address) that surrounds memory allocations with poisoned "redzones." Any read or write that touches one is caught immediately and reported with the exact faulting address and a stack trace — much more precise than waiting for a random crash.

Why are stack canaries and ASan turned off for some levels?

To make the underlying vulnerability visible rather than immediately blocked. Each mitigation is disabled deliberately, one at a time, exactly where needed — never by default — which also makes a good viva topic: what each protection actually does, and why disabling it changes the outcome.

I got "Cannot create temporary file: Read-only file system" — now what?

The sandbox's root filesystem is intentionally read-only. Compile into the writable scratch area instead, e.g. -o /tmp/vuln, which is mounted as a separate writable+executable tmpfs.

What's actually different between vuln.c and secure.c?

Never the overall program — only the one function under study, swapped for its bounds-aware counterpart (gets→fgets, strcpy→strncpy, strcat→strncat, sprintf→snprintf, a clamped memcpy length, or a validated array index). Same input, different outcome.

Why does this matter outside a classroom?

Buffer overflows are catalogued under CWE-120 and remain a recurring root cause in real CVEs — including the 1988 Morris Worm, which exploited a gets()-style overflow. They're a major reason memory-safe languages like Rust exist.
