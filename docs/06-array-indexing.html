CSS-LAB-BOA / level 06

Array Indexing — Invalid IndexREQUIRED

C performs no bounds checking on array access at all, in either direction — too large or negative are equally unchecked.

1. Overview & Vulnerability Theory

The vulnerable function

arr[idx] = value — array indexing in C is pure pointer arithmetic: arr[idx] is shorthand for *(arr + idx). The compiler has no built-in concept of 'is idx within this array's declared bounds' — that check, if it exists, has to be written explicitly by the programmer.

Why it fails at the memory level

Because arr[idx] is just an address computation, an out-of-range idx doesn't fail — it simply computes a different, valid-looking memory address and reads or writes there. A positive idx too large walks past the array's end into whatever's next on the stack; a negative idx walks backward, before the array's start, into whatever preceded it. Both are equally valid as far as the CPU is concerned.

higher addresses ┌─────────────────────────┐ │ ... │ <- idx >= 10 lands here ├─────────────────────────┤ │ int arr[10] │ ├─────────────────────────┤ │ ... │ <- idx < 0 lands here └─────────────────────────┘ lower addresses Unlike every other level in this lab, this overflow isn't driven by a copy length — it's driven directly by an attacker-controlled index value.

Classification

CWE-129 / CWE-787 / CWE-125 — CWE-129 (Improper Validation of Array Index); manifests as CWE-787 (Out-of-bounds Write) on the positive-index case demonstrated here, and would be CWE-125 (Out-of-bounds Read) for a read-only variant.

Reading the ASan trace, line by line

stack-buffer-overflow vs stack-buffer-underflow
ASan distinguishes direction: 'overflow' means the access landed past the end of the array; 'underflow' means it landed before the start. Both are reported, unlike with a string-length-driven overflow which is always in the 'overflow' direction.
WRITE of size 4
4 bytes, matching sizeof(int) -- confirms this is exactly one array-element-sized write landing out of bounds, not a multi-byte string copy.
#0 ... in vulnerable_index vuln.c:9
Points directly at the assignment arr[idx] = value; -- the exact line where the unchecked index was used.
SUMMARY: ... stack-buffer-overflow / underflow
One-line verdict, useful for quickly distinguishing which direction a given test case violated.

3. The Secure Rewrite

vuln.c

#include <stdio.h>
#include <stdlib.h>

void vulnerable_index(int idx, int value) {
    int arr[10];
    for (int i = 0; i < 10; i++) arr[i] = i;

    arr[idx] = value;
    /* VULNERABLE: idx never validated,
       can be negative or >= 10 */
    printf("arr[%d] = %d\n", idx, arr[idx]);
}

secure.c

#include <stdio.h>
#include <stdlib.h>

void secure_index(int idx, int value) {
    int arr[10];
    for (int i = 0; i < 10; i++) arr[i] = i;

    if (idx < 0 || idx >= 10) {
        printf("Rejected: index %d is out of "
               "bounds [0, 10)\n", idx);
        return;
    }
    arr[idx] = value;
    printf("arr[%d] = %d\n", idx, arr[idx]);
}

What changed, and why it's actually safe

There is no 'safe indexing function' to swap in — C offers no bounds-checked array access at the language level. The only fix is an explicit, manual range check (0 <= idx < 10) before the access ever happens. This is the one level in this lab where the fix is pure application logic, not a library substitution.

Proof: same malformed input, secure build

$ /tmp/secure 15 1
Rejected: index 15 is out of bounds [0, 10)
Returned safely.

$ /tmp/secure -5 1
Rejected: index -5 is out of bounds [0, 10)
Returned safely.
