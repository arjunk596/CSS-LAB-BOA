CSS-LAB-BOA / level 05

memcpy() — Incorrect Byte CountREQUIRED

The function itself behaves perfectly correctly. The vulnerability is entirely in trusting a byte count nobody validated.

1. Overview & Vulnerability Theory

The vulnerable function

memcpy(dest, src, len) — copies exactly len bytes from src to dest. There's no bug in what memcpy() does — it does precisely what it's told. The bug is that len, here, comes straight from the caller with no upper-bound check against dest's actual size.

Why it fails at the memory level

This level demonstrates a more subtle variant: the overflow can be made to land precisely on an adjacent variable (access_granted) without ever touching further memory, which means a carefully-sized overflow can silently corrupt program state without crashing at all — no ASan trip, no visible symptom, just a flipped boolean the program now trusts. This is closer to how real-world memory-corruption bugs are actually exploited than a loud crash is.

higher addresses ┌─────────────────────────┐ │ saved return address │ ├─────────────────────────┤ │ saved base pointer │ ├─────────────────────────┤ │ int access_granted │ <- precisely-sized overflow lands exactly here ├─────────────────────────┤ │ char buffer[16] │ <- memcpy writes len bytes starting here └─────────────────────────┘ lower addresses

Classification

CWE-120 / CWE-787 — Buffer Copy without Checking Size of Input; CWE-787 (Out-of-bounds Write) is the more precise classification here, since the root issue is an unvalidated length parameter rather than an unbounded string operation.

3. The Secure Rewrite

vuln.c

#include <stdio.h>
#include <string.h>

void vulnerable_copy(char *input, int len) {
    char buffer[16];
    int access_granted = 0;

    memcpy(buffer, input, len);
    /* VULNERABLE: len is caller-controlled,
       never checked against sizeof(buffer) */
    buffer[15] = '\0';

    printf("Buffer: %s\n", buffer);
    if (access_granted != 0)
        printf("FLAG: solved\n");
}

secure.c

#include <stdio.h>
#include <string.h>

void secure_copy(char *input, int len) {
    char buffer[16];
    int access_granted = 0;

    if (len < 0) {
        fprintf(stderr, "Rejected\n");
        return;
    }
    int safe_len = len;
    if ((size_t)safe_len > sizeof(buffer) - 1)
        safe_len = sizeof(buffer) - 1;
    memcpy(buffer, input, (size_t)safe_len);
    buffer[safe_len] = '\0';

    printf("Buffer: %s\n", buffer);
    printf("access_granted is %d.\n",
           access_granted);
}

What changed, and why it's actually safe

Two checks, not one: first, len is rejected outright if negative (a negative value cast to size_t for memcpy's length parameter is undefined behavior — a real bug fixed in this project after a security review flagged it). Second, len is clamped to the buffer's actual capacity before the copy ever happens. memcpy() itself needs no safer replacement — the fix is entirely about validating the argument, not changing the function.

Proof: same malformed input, secure build
