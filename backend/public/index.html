EXPERIMENT 04 — SYSTEM SECURITY

Aim and Objectives

Aim: To understand and demonstrate memory corruption vulnerabilities in low-level compiled languages, specifically analyzing how unbounded user input can overwrite adjacent stack memory in a Stack-Based Buffer Overflow Attack (Smashing the Stack), hijack the CPU instruction pointer (EIP/RIP), and redirect execution flow to attacker-controlled code or arbitrary functions.

Learning Objectives

  1. Process Memory Architecture: Understand the layout of a binary in virtual memory, including Text/Code, Data, BSS, Heap, and Stack segments.
  2. Stack Frame Dynamics: Analyze function call mechanics, stack pointer (ESP/RSP), frame base pointer (EBP/RBP), and how function return addresses are placed on the call stack.
  3. Vulnerable C Functions: Identify classical unchecked memory functions (gets, strcpy, strcat, sprintf, memcpy, and unvalidated array indexing) that fail to enforce buffer bounds.
  4. Control Flow Hijacking: Formulate crafted string inputs that overwrite adjacent flags, alter program logic, and manipulate the saved return address.
  5. Modern Mitigations & Hardening: Evaluate defensive technologies including Stack Canaries (-fstack-protector), Non-Executable Stack (DEP/NX), Address Space Layout Randomization (ASLR), and AddressSanitizer (ASan).
Educational Sandboxing: This virtual laboratory runs isolated within disposable Docker containers on Ubuntu with AddressSanitizer support. Compiler protections are deliberately isolated so students can examine both vulnerable and hardened implementations safely.

Expected Outcomes

  • Understand the root cause of spatial memory violations in low-level languages.
  • Observe memory corruption in real-time via the interactive WebAssembly memory visualizer.
  • Successfully exploit and capture flags in the 7 hands-on vulnerability sandbox levels.
  • Implement defensive coding practices utilizing bounded string functions (e.g., fgets, strncpy, snprintf).

EXPERIMENT 04 — THEORY

Theory: Memory Layout & Stack Smashing

A buffer is a contiguous block of physical or virtual memory allocated to hold data such as character strings or arrays. Because C and C++ do not provide automatic array bounds checking, writing beyond the allocated capacity causes data to overwrite adjacent memory allocations.

1. Virtual Memory Organization

When an ELF or Mach-O executable runs, its virtual address space is organized into distinct segments:

Segment Address Range Purpose & Description
Stack High Memory (grows downwards) Stores local function variables, call frames, saved registers, and return addresses.
Heap Low Memory (grows upwards) Dynamic memory allocations managed at runtime via malloc() and free().
BSS & Data Low Memory Uninitialized (BSS) and initialized global and static variables.
Text (Code) Lowest Memory (Read-Only) Compiled CPU machine instructions of the program.

2. Anatomy of a Call Stack Frame

Each time a function is called, a new stack frame is pushed onto the stack. A typical x86/x64 stack frame contains:

[Function Arguments] → [Return Address (RET)] → [Saved Frame Pointer (EBP)] → [Local Buffer Variables]

The Critical Vulnerability: While the call stack grows downward (from higher to lower memory addresses), character buffers write upward (from lower to higher memory addresses). Therefore, when user input overflows a local buffer, it directly spills into the Saved Frame Pointer and the Return Address!

The Exploitation Vector: If an attacker provides an input payload longer than the buffer, the excess bytes overwrite the return address. When the function executes the RET instruction, the CPU pops the attacker-supplied address into the Instruction Pointer (EIP/RIP), redirecting program execution.

3. Vulnerable Functions vs. Secure Counterparts

Vulnerable C API Defect Mechanism Secure Modern Replacement
gets(buffer) Reads until newline with no bounds check. Removed from ISO C11. fgets(buffer, sizeof(buffer), stdin)
strcpy(dst, src) Copies until null byte (\0), ignoring destination size. strncpy(dst, src, sizeof(dst) - 1) or strlcpy
strcat(dst, src) Appends without verifying available destination room. strncat(dst, src, sizeof(dst) - strlen(dst) - 1)
sprintf(buf, fmt, ...) Formats string without maximum length restraint. snprintf(buf, sizeof(buf), fmt, ...)
memcpy(dst, src, len) Fails when caller controls len or signed integer overflow occurs. Explicit bounds validation: if (len ≤ sizeof(dst))

4. Modern Compiler & Operating System Defenses

  • Stack Canaries (StackGuard): A random canary word placed between local buffers and the saved frame pointer. Before returning, the function verifies the canary is intact; if altered, __stack_chk_fail() terminates the process.
  • DEP / NX (Non-Executable Stack): CPU hardware page table protection marking stack pages as non-executable (No-Execute bit), preventing execution of injected shellcode.
  • ASLR (Address Space Layout Randomization): Randomizes the base addresses of stack, heap, and shared libraries on each program invocation, making hardcoded exploit addresses ineffective.

EXPERIMENT 04 — PROCEDURE

Procedure: Sandbox & Exploitation Guide

Follow this experimental procedure to explore each vulnerability class inside the live Docker sandbox.

Step 1 — Understand Stack Overflow via the Visualizer

  1. Navigate to the Interactive Simulation tab.
  2. Use the WASM Stack Visualizer to test inputs of lengths 8, 16, 20, and 24 bytes.
  3. Observe how the memory cells highlight in blue for safe buffer storage, and turn red when spilling into the adjacent stack canary and frame pointer regions.

Step 2 — Connect to the Disposable Sandbox Shell

  1. Verify the status indicator displays ● connected in the live terminal pane.
  2. Inspect the current directory:
    ls -la /opt/levels

Step 3 — Level 01: Unbounded Read with gets()

  1. Navigate into the 01-gets directory and compile the vulnerable source code:
    cd /opt/levels/01-gets && gcc -g -fsanitize=address -fno-stack-protector -o /tmp/v vuln.c
  2. Run the program with a legitimate small input (under 16 bytes):
    echo "CyberLab" | /tmp/v
  3. Trigger the overflow using an oversized payload:
    python3 -c "print('A'*40)" | /tmp/v
  4. Notice how AddressSanitizer immediately intercepts the stack-buffer-overflow and emits a detailed memory crash report.

Step 4 — Progress Through Remaining Levels

Proceed through Levels 02 (strcpy), 03 (strcat), 04 (sprintf), 05 (memcpy), 06 (array indexing), and 07 (bonus return address redirect). Compare each vulnerable implementation with its corresponding safe rewrite!

EXPERIMENT 04 — HANDS-ON CATALOG

Exploit Levels & Vulnerability Breakdown

Each level isolates a specific memory corruption vulnerability pattern. Click each level to examine the vulnerable C call, review the trigger commands, copy the exploit string, and inspect the safe fix.

Vulnerability: gets() reads characters from standard input until it encounters a newline, without respecting destination buffer capacity.

cd /opt/levels/01-gets && gcc -g -fsanitize=address -fno-stack-protector -o /tmp/v vuln.c echo "NormalInput" | /tmp/v python3 -c "print('A'*40)" | /tmp/v

Safe Remediation: fgets(buffer, sizeof(buffer), stdin)

Vulnerability: strcpy() copies bytes until finding a null terminator, ignoring destination bounds.

cd /opt/levels/02-strcpy && gcc -g -fsanitize=address -fno-stack-protector -o /tmp/v vuln.c /tmp/v "ValidArg" /tmp/v "$(python3 -c "print('A'*40)")"

Safe Remediation: strncpy(buffer, src, sizeof(buffer) - 1); buffer[sizeof(buffer)-1] = '\0';

Vulnerability: strcat() appends source string bytes onto destination without checking whether remaining space suffices.

cd /opt/levels/03-strcat && gcc -g -fsanitize=address -fno-stack-protector -o /tmp/v vuln.c /tmp/v "FirstPart" "SecondPart" /tmp/v "$(python3 -c "print('A'*20)")" "$(python3 -c "print('B'*20)")"

Safe Remediation: strncat(dest, src, sizeof(dest) - strlen(dest) - 1)

Vulnerability: sprintf() formats and writes data into a buffer without receiving maximum length bounds.

cd /opt/levels/04-sprintf && gcc -g -fsanitize=address -fno-stack-protector -o /tmp/v vuln.c /tmp/v "Alice" 100 /tmp/v "$(python3 -c "print('A'*40)")" 100

Safe Remediation: snprintf(dest, sizeof(dest), "User: %s (id: %d)", user, id)

Vulnerability: The program copies n bytes directly into a buffer where n is caller-supplied or subject to integer overflow.

cd /opt/levels/05-memcpy && gcc -g -fsanitize=address -fno-stack-protector -o /tmp/v vuln.c /tmp/v 8 "12345678" /tmp/v 40 "$(python3 -c "print('A'*40)")"

Safe Remediation: Validate length strictly: if (len > sizeof(buf)) { return -1; }

Vulnerability: Writing to an array via an unconstrained integer index allows arbitrary displacement overwrites outside the array boundary.

cd /opt/levels/06-array-indexing && gcc -g -fsanitize=address -fno-stack-protector -o /tmp/v vuln.c /tmp/v 2 99 /tmp/v 12 1337

Safe Remediation: Explicit range validation: if (idx >= 0 && idx < MAX_ELEMENTS)

Vulnerability: Overwrites the saved Return Address (RET) on the stack to redirect instruction execution to the secret target function win().

cd /opt/levels/07-bonus-redirect && make ./exploit.sh

Safe Remediation: Enable compiler stack canaries: gcc -fstack-protector-all and shadow stacks.

EXPERIMENT 04 — DOCUMENTATION

Frequently Asked Questions & References

Frequently Asked Questions

Why was gets() removed from modern C standards?

Because gets() only accepts a pointer to the destination buffer with no size parameter, it is fundamentally impossible to use safely with untrusted input. It was deprecated in ISO C99 and formally removed in ISO C11.

How does AddressSanitizer (ASan) detect buffer overflows?

AddressSanitizer surrounds all heap, global, and stack variables with "poisoned redzones" in shadow memory. Every load and store operation is instrumented at compile-time to check if the target memory is poisoned. Accessing a redzone immediately triggers an ASan crash report.

Does ASLR alone prevent buffer overflow exploitation?

No. While ASLR randomizes base addresses, attackers can bypass it using memory leak vulnerabilities to discover addresses, or use relative displacements in partial overwrites. Robust defense requires defense-in-depth: bounds checking, canaries, DEP/NX, and ASLR combined.
